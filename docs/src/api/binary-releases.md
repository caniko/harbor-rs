# Binary release archives

## Publisher-owned static archives

`harbor.lib.rust.mkUpstreamBinaryPackage` installs static Linux executables from
publisher-owned `tar.gz`, `tar.xz`, or already-unpacked sources. It accepts an
explicit installed-name-to-source mapping and preserves executable bytes.
`mkReleaseBinaryPackage` retains its independent Harbor-manifest contract.

```nix
harbor.lib.rust.mkUpstreamBinaryPackage {
  inherit pkgs;
  pname = "example";
  version = "1.2.3";
  sources.x86_64-linux = pkgs.fetchurl {
    url = "https://example.org/releases/1.2.3/example-x86_64-linux-musl.tar.gz";
    hash = "sha256-...";
  };
  binaries.example = "example-1.2.3/example";
  meta.mainProgram = "example";
}
```

Only `x86_64-linux` and `aarch64-linux` targets are supported. The default is
`pkgs.stdenv.hostPlatform.system`; an explicit `targetSystem` selects an archive
for another supported architecture without executing its contents during
installation. Mappings are relative to the source tree or archive root, including
any enclosing directory. A locked tarball input may strip an enclosing directory;
use the returned tree's layout for already-unpacked sources.

Destination names must be safe filename components. Source paths cannot contain
absolute, empty, `.` or `..` components or line breaks. Every path component must
be nonsymlink, and the payload must be a regular static ELF executable for the
selected machine. Interpreters, dynamic dependencies, relocatable objects, core
dumps and shared libraries without an executable entry point are rejected. Static
PIE is accepted only with a nonzero entry point in executable, file-backed
`PT_LOAD` data. Fixup is disabled.

Sources must be executable by default. For publishers that archive executable
ELF payloads with mode `0644`, set `requireExecutable = false` explicitly. Other
validation remains enforced; installation sets `0755` without changing contents.

Callers own fixed-output hashes or locked non-flake inputs, provenance and
signature verification, licenses, feature compatibility, and runtime
qualification. This constructor does not infer wrappers, runtime libraries,
manifests or auxiliary assets, and does not contact provenance services during
evaluation or build.

The v1-compatible `mkBinaryRelease` packages one or more already-built binaries into a
deterministic, static MUSL archive. The archive contains `bin/` and a
`manifest.json` describing the package name, version, Nix system, Rust target,
and exact binary list. `mkReleaseBinaryPackage` consumes an unpacked archive
from a locked `flake = false` input and validates that contract before
installing the binaries. Keep this schema when existing consumers already
consume v1 archives; new multi-format release wiring should use the generic
v2 constructors below.

The producer and consumer are deliberately separate. A project keeps its
source-built package for development and exposes the prebuilt package as an
explicit opt-in output:

```nix
let
  release = harbor-rs.lib.mkBinaryRelease {
    inherit pkgs;
    pname = "my-tool";
    version = "1.2.3";
    artifacts = {
      x86_64-linux-musl = {
        package = packages.my-tool-x86_64-linux-musl;
        system = "x86_64-linux";
        rustTarget = "x86_64-unknown-linux-musl";
        binaries = ["my-tool"];
      };
      aarch64-linux-musl = {
        package = packages.my-tool-aarch64-linux-musl;
        system = "aarch64-linux";
        rustTarget = "aarch64-unknown-linux-musl";
        binaries = ["my-tool"];
      };
    };
  };
in
{
  packages.release-bundle = release.releaseBundle;
}
```

A consumer pins each supported release asset as a non-flake input, verifies
the published Simit checksum signature before changing its lock file, then
selects the matching input:

```nix
inputs.my-tool-bin-x86_64.url =
  "https://codeberg.org/example/my-tool/releases/download/1.2.3/my-tool-1.2.3-x86_64-linux-musl.tar.gz";
inputs.my-tool-bin-x86_64.flake = false;

packages.my-tool-prebuilt = harbor-rs.lib.mkReleaseBinaryPackage {
  inherit pkgs;
  pname = "my-tool";
  version = "1.2.3";
  sources.x86_64-linux = inputs.my-tool-bin-x86_64;
  binaries = ["my-tool"];
};
```

The helper fails closed when the current system has no matching input or the
archive manifest is inconsistent. The release workflow is generated by
`simit init release`; it builds the bundle on `atlas-nix-trusted`, publishes
the archives to Codeberg, and signs the checksum manifest with the committed
`keys/minisign.pub` trust root.

Before the first tag, provision the generated workflow's required secrets:
`CODEBERG_TOKEN` at user scope, and a dedicated harbor-rs
`MINISIGN_SECRET_KEY`/`MINISIGN_PASSWORD` pair at repository scope. The public
key in `keys/minisign.pub` must be the matching key; do not reuse another
project's signing key. Check the contract with
`simit release secrets contract --json` and the Canix declaration with
`canix release secrets check --project /path/to/harbor-rs`.

## Portable native applications

Applications that cannot satisfy the static ELF contract can use the pinned
`nix-bundle` backend:

```nix
let
  release = harbor-rs.lib.mkPortableBinaryRelease {
    inherit pkgs;
    pname = "my-app";
    version = "1.2.3";
    artifacts.x86_64-linux.entries.my-app.package = packages.my-app;
  };
in {
  packages.release-bundle = release.releaseBundle;
}
```

The resulting archive contains a self-extracting executable and a v2
`manifest.json` with `format = "nix-bundle"`. Consumers use
`mkPortableReleaseBinaryPackage` with a locked `flake = false` archive. The
bundle remains dependent on the host kernel and hardware interfaces (for
example GPU drivers or PipeWire), which must be smoke-tested before switching
the production module.

## Generic release bundles

Projects with more than one release format can use the format-neutral
constructors. `mkReleaseArtifact` exposes one flat file, `mkReleaseArchive`
stages named files into a deterministic `tar.gz` or `zip`, and
`mkReleaseBundle` combines those outputs and writes one versioned
`*-release-manifest.json`. The configured bundle set is the explicit input
consumed by Simit's `[release.artifacts].nix_bundle_attrs` list and must
produce exactly one versioned manifest; project-specific
`build_commands` remain additive for formats that need extra signing or
installer work.

```nix
let
  archive = harbor-rs.lib.mkReleaseArchive {
    inherit pkgs;
    pname = "my-tool";
    version = "1.2.3";
    name = "my-tool-1.2.3-x86_64-linux.tar.gz";
    package = packages.my-tool;
    entries = {"bin/my-tool" = "bin/my-tool";};
    system = "x86_64-linux";
    rustTarget = "x86_64-unknown-linux-gnu";
  };
in
{
  packages.release-bundle = harbor-rs.lib.mkReleaseBundle {
    inherit pkgs;
    pname = "my-tool";
    version = "1.2.3";
    artifacts = {inherit archive;};
  };
}
```

## cargo-binstall metadata

Every release bundle (`mkReleaseBundle`, and the `releaseBundle` of
`mkBinaryRelease` and `mkPortableBinaryRelease`) exposes `binstall`: the
`[package.metadata.binstall]` overrides that point `cargo binstall <crate>` at
its `tar.gz`/`zip` binary archives, one override per Rust target the archive
runs on. Static and nix-bundle Linux archives serve both `-gnu` and `-musl`
hosts. The URL uses the crate's `repository` and simit's bare `<version>` tag;
pass `binstallTagPrefix = "v"` to the bundle helper for `v<version>` tags.
AppImages, wheels and other opaque files are not considered.

Wire it as a flake check against the crate that owns the binaries:

```nix
checks.binstall-metadata = harbor-rs.lib.mkBinstallCheck {
  inherit pkgs;
  bundle = packages.release-bundle;
  cargoToml = ./crates/my-tool/Cargo.toml;
};
```

The check fails until the manifest has `package.repository` and exactly the
generated block, and until every archive ships each `[[bin]]` without
`required-features` (binstall refuses partial archives at install time). A
hand-made `mkReleaseArtifact` archive must pass `binaries`, its archive-relative
executable paths such as `["bin/my-tool"]`. Write
the block with
`nix eval --raw .#checks.x86_64-linux.binstall-metadata.toml >> crates/my-tool/Cargo.toml`
and replace it the same way after the archive set changes.

## One-call binstall releases

`lib.mkBinstallRelease` wires the whole cargo-binstall path for a workspace:
`mkCrossPackages` builds every binary once per target, `mkReleaseArchive` packs
them under `bin/`, `mkReleaseBundle` publishes the archives, and `mkBinstallCheck`
guards each crate's metadata.

```nix
let
  release = harbor-rs.lib.mkBinstallRelease {
    inherit pkgs system;
    pname = "my-tool";
    version = "1.2.3";
    commonArgs = {
      src = ./.;
      strictDeps = true;
    };
    crates.my-tool = {cargoToml = ./Cargo.toml;};
    # Defaults:
    # targets = {
    #   x86_64-linux = ["x86_64-linux-musl" "aarch64-linux-musl" "windows"];
    #   aarch64-darwin = ["native"];
    # };
  };
in {
  packages.release-bundle = release.releaseBundle;
  checks = release.checks;
}
```

`targets` maps each build system to the `mkCrossPackages` targets that system
builds. A host builds only its own entry (`release.packages` holds those
derivations), so the returned `releaseBundle` is `null` on a system that is not
listed. Every archive is named `<pname>-<version>-<rustTarget>.tar.gz` (`.zip`
on Windows) and contains all non-gated binaries of all listed crates, so one
bundle serves every crate.

`crates` names each published crate and points at its `Cargo.toml`; its
`[[bin]]` entries without `required-features` (or `package.name` when there are
none) are the binaries binstall expects. The build uses `commonArgs` as-is: a
virtual workspace already builds every member, while a root-package workspace
needs `cargoExtraArgs = "--workspace"` so sibling crates are built too. The
archive step fails loudly when a listed binary was not produced. `release.binstall` is the union
`[package.metadata.binstall]` for **all** systems in `targets`, not only the
current one, and it is derived from data (target names plus manifests), so any
system renders the identical block without evaluating another system's
toolchain. `release.archives` exposes those synthetic descriptors and
`release.checks` carries one `binstall-metadata` check (or
`binstall-metadata-<crate>` per crate in a workspace) with `passthru.toml` and
`passthru.matches`.

Pass `tagPrefix = "v"` for `v<version>` release tags, `cross` to reuse a
`mkCross` you already built, `toolchainArgs` to pin the Rust channel or disable
the compiler cache, and `targetArgs.<target>` for per-target crane arguments
such as `doCheck = false`.

Simit publishes the union from per-system runners: enable
`[release.artifacts] prebuild_binaries = true` (equivalent to
`nix_bundle_attrs = ["release-bundle"]`), and add every release system to
`[package.metadata.simit.prebuild.system_runners]` (or
`[ci.nix_system_runners]`) so `aarch64-darwin` builds the Mach-O archive next to
the Linux and Windows ones. The release job uploads all archives to one tag;
the union block in the crate manifest is what lets `cargo binstall` pick the
right one on each host.

Write the block from the check that runs on your build host:

```bash
nix eval --raw .#checks.x86_64-linux.binstall-metadata.toml >> Cargo.toml
```

For a multi-crate workspace use the per-crate key, for example
`.#checks.x86_64-linux.binstall-metadata-my-tool.toml`, and append it to that
crate's manifest.
